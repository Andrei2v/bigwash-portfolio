# BigWash

Клієнтська частина панелі керування автомийкою: статистика, клієнти, картки, операції та налаштування обладнання. Серверна частина на Go (Gin + MySQL) розміщується окремо. Для розробки інтерфейсу передбачено автономний DEV-режим.

## Технології

- SvelteKit 2, Svelte 5, JavaScript, Vite.
- Chart.js для графіків, Axios і Fetch API для запитів.
- Lucide для іконок; локалізація UA/RU, світла й темна теми.

| --- | --- |
| `/login` | Вхід і реєстрація |

| `/clients` | Клієнти |

Маршрут `/` перенаправляє на статистику або форму входу залежно від стану сесії. Доступність окремих дій залежить від режиму та підключеного API; наявність форми не означає завершену серверну інтеграцію.

## Установлення та локальний запуск

Потрібні Node.js LTS, npm і сучасний браузер. Виконуйте команди з кореня проєкту.

```sh
npm ci
```

Створіть `.env` з [`.env.example`](.env.example), зберігши наявну конфігурацію, якщо вона вже є.

PowerShell:

```powershell
if (!(Test-Path .env)) { Copy-Item .env.example .env }
```

Linux/macOS:

```sh
[ -e .env ] || cp .env.example .env
```

Запустіть сервер розробки:

```sh
npm run dev
```

Відкрийте адресу з термінала, зазвичай `http://localhost:5173`, і зареєструйте власний тестовий обліковий запис на `/login`. Спільний обліковий запис із заданим паролем автоматично не створюється.

На Windows можна скористатися `start-dev.bat`: він створює відсутній `.env` із прикладу та встановлює залежності за потреби. `start-demo.bat` запускає локальний DEV-режим із демонстраційними даними; частина дій у ньому обмежена. Обидва варіанти використовують ту саму локальну реєстрацію.

### Телефон у локальній мережі (Windows)

HTTP-адреса на кшталт `http://192.168.0.126:5173` не є захищеним контекстом: Chrome не надає їй Web Crypto API, потрібний для PBKDF2. HTTP localhost має виняток лише на самому комп’ютері. Прапорець `VITE_LOCAL_MODE` від адреси не залежить; Go backend для локальної реєстрації не потрібний.

1. Переконайтеся, що у вашій локальній конфігурації явно встановлено `VITE_LOCAL_MODE=true`. Під’єднайте телефон і ноутбук до однієї довіреної мережі Wi-Fi.
2. Запустіть `start-dev-lan.bat`. Якщо знайдено кілька приватних IP, укажіть потрібний: `start-dev-lan.bat 192.168.0.126`. Потрібні Windows PowerShell і .NET Framework 4.7.2 або новіший. Скрипт слухає лише вибрану приватну IPv4-адресу та не змінює звичайний `start-dev.bat` на localhost:5173.
3. Перший запуск створює в `.local/https/` сертифікати. Передайте на телефон **лише публічний `rootCA.cer`** довіреним способом. У налаштуваннях Android знайдіть «Встановити сертифікат» → «Сертифікат центру сертифікації / CA» та виберіть цей файл. Назви меню залежать від версії Android. Довіряйте лише власному згенерованому сертифікату; його SHA-256 відбиток показано в консолі. Скрипт не встановлює довіру автоматично. Після завершення роботи цей CA можна видалити з користувацьких сертифікатів телефона.
4. Якщо Windows Firewall запитає дозвіл для Node.js, надайте його лише для приватної мережі. Відкрийте HTTPS-адресу з консолі, зазвичай `https://192.168.0.126:5174/login`, без попередження про сертифікат. Зареєструйте власний DEV-акаунт і ввійдіть. Не вимикайте перевірку TLS або захист Chrome.

Сертифікат містить вибраний IP і діє один рік. Повторний запуск використовує ті самі файли. Якщо IP змінився чи сертифікат прострочено, зупиніть LAN-сервер, перейменуйте каталог `.local/https`, запустіть його знову та встановіть новий публічний CA на телефоні. Старі файли автоматично не замінюються. За потреби зафіксуйте IP ноутбука в DHCP налаштуваннях роутера.

`server.pfx` містить приватний ключ: його не можна передавати, публікувати чи додавати до Git. Каталог `.local/` ігнорується Git і недоступний через LAN-сервер Vite. Приватний ключ CA не зберігається. Використовуйте цей запуск лише для DEV у довіреній мережі, без реальних паролів і персональних даних.

**Сховища ізольовані за браузером, протоколом, адресою та портом.** Акаунт з HTTP localhost на ноутбуці не переноситься на HTTPS телефона. Після переходу на HTTPS потрібно зареєструватися в цьому браузері; попередні HTTP-акаунти й дані залишаються на старій адресі, скрипт їх не очищує. LAN-запуск відмовляється працювати без явного локального DEV-режиму; production-збірка й preview продовжують використовувати Go API.

## Змінні середовища та DEV/PROD

| Змінна | Призначення |
| --- | --- |
| `VITE_LOCAL_MODE` | Явний дозвіл на локальну авторизацію та локальний API у DEV |
| `VITE_DEMO_MODE` | Додатковий демонстраційний режим; працює лише разом із локальним DEV-режимом |
| `VITE_API_URL` | Базова адреса Go API з префіксом `/api/v1` |
| `VITE_WS_URL` | Адреса WebSocket-сервера |
| `VITE_TELEGRAM_SUPPORT_URL` | Необов’язкове публічне HTTPS-посилання `https://t.me/<username>` для ручного переходу зі звіту про помилку; без токена бота |

У `.env.example` встановлено `VITE_LOCAL_MODE=true` і `VITE_DEMO_MODE=false`. Локальна авторизація дозволена лише за умови `DEV && !PROD && VITE_LOCAL_MODE === 'true'`. Без явного дозволу клієнт використовує Go API.

Кожна збірка й production-preview примусово вимикають локальний і демонстраційний режими, зокрема під час `npm run build -- --mode development`. Недоступність Go API не вмикає локальний вхід. Production не приймає локальні токени, а відновлення серверної сесії потребує підтвердження від Go API.

**Змінні `VITE_*` публічні:** їхні значення можуть потрапляти до клієнтської збірки. Не зберігайте в них паролі, приватні ключі, токени чи доступи до бази даних. Файл `.env` не слід додавати до Git.

## Локальні облікові записи та дані

Реєстрація й вхід у локальному DEV-режимі працюють без Go backend. Для хешування паролів потрібен Web Crypto API, доступний на localhost або через HTTPS. Пароль має містити щонайменше шість символів. Після реєстрації потрібно увійти окремо.

Облікові записи зберігаються в IndexedDB; за її відсутності використовується localStorage. Підтримуються й раніше збережені записи localStorage. Дані належать конкретному браузеру та адресі сайту, включно з протоколом і портом, і не синхронізуються між пристроями.

Перезавантаження сторінки відновлює сесію. Вихід завершує її, але не видаляє облікові записи й дані розділів. Зміна `.env` не змінює дані входу. Записи в розділі «Адміністратори» зберігаються окремо від облікових записів авторизації.

**Локальна авторизація призначена лише для розробки.** Вона не забезпечує серверного контролю доступу. Не використовуйте в цьому режимі реальні паролі, персональні чи платіжні дані. Не очищуйте сховища браузера, якщо потрібно зберегти локальні записи.

### Зміна email і пароля в DEV

У консолі браузера на локальному DEV-сайті виконайте:

```js
const { changeLocalCredentials } = await import('/src/lib/api/client.js');
await changeLocalCredentials(
  prompt('Поточний email'),
  prompt('Поточний тестовий пароль'),
  prompt('Новий email'),
  prompt('Новий тестовий пароль')
);
```

Функція перевіряє поточний пароль і змінює дані вибраного облікового запису, зберігаючи його ID, роль та інші записи. Після успішного збереження поточна DEV-сесія завершується; наступний вхід потребує нових даних. Помилка запису IndexedDB не маскується успішним записом в інше сховище. Функція недоступна поза локальним DEV-режимом.

Не записуйте паролі безпосередньо в код консолі чи конфігурацію. Поле `prompt` не приховує введені символи, тому використовуйте лише окремі тестові паролі.

Медіаповідомлення пультів зберігаються в окремій IndexedDB `bigwash-media-v1`: текст і файли записуються разом після підтвердження. Старі текстові налаштування localStorage не видаляються. Дозволено PNG/JPEG/WebP/GIF до 2 МБ, до 10 зображень у повідомленні та до 50 МБ файлів у цьому сховищі. Потрібна доступна IndexedDB; помилка сховища не позначається як успішне збереження.

## Підключення Go API та production-збірка

Для роботи із сервером вимкніть локальні режими й задайте адреси API та WebSocket. Приклад для Go backend на локальному комп’ютері:

```dotenv
VITE_LOCAL_MODE=false
VITE_DEMO_MODE=false
VITE_API_URL=http://localhost:8080/api/v1
VITE_WS_URL=ws://localhost:8080/api/v1/ws
```

Після зміни конфігурації перезапустіть Vite. Для розгорнутого середовища використовуйте HTTPS і WSS. Перелік клієнтських запитів наведено в [API_CONTRACT.md](API_CONTRACT.md); звірте маршрути, поля відповідей, авторизацію та CORS з актуальним Go API. Це довідник викликів фронтенда, а не узгоджена серверна специфікація.

Адреси API та WebSocket потрібно задати **до збірки**:

```sh
npm run build
npm run preview
```

`npm run preview` показує production-збірку локально. Для входу, реєстрації та серверних даних потрібен доступний Go API; автономна DEV-авторизація тут не працює. Зміна `.env` після збірки не оновлює вже створені клієнтські файли.

Preview не замінює розгортання. Зараз використовується `@sveltejs/adapter-auto`; для цільової платформи потрібно налаштувати відповідний адаптер SvelteKit.

## Перевірки

```sh
node --test --test-concurrency=1 tests/*.test.mjs
npm run build
```

Тести перевіряють DEV/PROD, авторизацію, семантичні ключі UA/RU, конфігурації та відсутність облікових даних у логах і JSON-експорті. DEV-браузерні набори потребують запущеного локального сервера й явного `BIGWASH_BROWSER_URL` (наприклад, `http://localhost:5173`). Production-preview перевіряється з `BIGWASH_PREVIEW_URL` та імітацією документованого Go API; це не перевірка справжнього backend. Для LAN-набору потрібні `BIGWASH_LAN_HTTP_URL`, `BIGWASH_LAN_HTTPS_URL` і `BIGWASH_LAN_CERT_DIR` із власними тестовими сертифікатами. Без відповідних змінних набори позначаються пропущеними. Для встановленого Chrome можна задати `BIGWASH_CHROME_PATH`. Тести використовують окремі тимчасові профілі й запускаються послідовно.

Команда `npm run check` є в `package.json`, але наразі не працює: у залежностях відсутній `svelte-check`, а в проєкті немає `jsconfig.json`.

## Відомі обмеження

- Реальний Go backend не проходив інтеграційної перевірки під час підготовки фронтенда. Production-авторизацію перевіряли з імітацією API; серверні CRUD-операції, платежі та WebSocket потребують окремого прогону.
- Частина дій залишається заглушками, зокрема видалення пульта. Локальний адаптер не реалізує всі серверні операції; непідтримувані запити повертають `501`.
- Демонстраційна статистика призначена для перевірки інтерфейсу й не є реальними фінансовими даними.
- Програми пульта й номери кнопок налаштовуються вручну в DEV; номери кнопок не обмежені 12 слотами реле. Фізичне визначення натискання, передавання медіа на термінал і копіювання програм між пультами ще не підключені.
- Реле мають 12 локальних DEV-слотів; пауза й Promo зберігають конфігурацію, але не керують обладнанням. Знижки не сумуються; пріоритет при збігу умов потрібно погодити перед Go-інтеграцією.
- DEV-карта використовує тайли [OpenStreetMap](https://operations.osmfoundation.org/policies/tiles/) і геокодер [Photon](https://github.com/komoot/photon/blob/master/README.md) без ключів. Пошук запускається користувачем; адреси/координати передаються зовнішньому сервісу, запити кешуються й обмежуються за частотою. Публічні сервіси не гарантують доступності; передбачено ручний ввід. Для production потрібно погодити власний сервіс/провайдера та Go-збереження.
- Перевірки виконувалися на Windows. Автоматичний тест перевіряє точний регістр шляхів імпорту; запуск у Linux-оточенні окремо не перевірено.
- Залишаються попередження доступності й невикористаних CSS-селекторів. Файл `/favicon.ico` відсутній.
