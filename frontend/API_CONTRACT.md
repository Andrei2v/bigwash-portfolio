# BigWash — ориентир для интеграции с Go API

Этот файл описывает **обнаруженные** вызовы в исходниках фронтенда. Это не полная спецификация backend и не гарантия совместимости. При интеграции сравните поля с актуальным сервером и протестируйте маршруты.

## Конфигурация

```dotenv
VITE_DEMO_MODE=false
VITE_API_URL=http://localhost:8080/api/v1
VITE_WS_URL=ws://localhost:8080/api/v1/ws
```

Для production используйте `https://` и `wss://`. В браузере авторизация реализована через Bearer token (значение `localStorage.token`); безопасность хранения и обновление токена требуют отдельной оценки. Не кладите секреты в переменные `VITE_*`.

Страницы Clients и Cards используют общий Axios-клиент из `src/lib/api/client.js`: в серверном режиме он добавляет `Authorization: Bearer ...` и обрабатывает защищённый ответ 401. Admin использует существующий fetch-сценарий с явным Bearer-заголовком. Это описание frontend; совместимость с реальным Go API требует интеграционной проверки.

## Примеры ответов, которые читает фронтенд

### Авторизация

```json
{
  "user": { "id": 1, "firstname": "Example", "lastname": "User" },
  "token": "JWT_OR_SESSION_TOKEN_FROM_YOUR_BACKEND"
}
```

### Дашборд

```json
{ "daily_stats": { "profit": 125521, "expenses": 25521, "balance": 100000 } }
```

### Клиенты (GET `/clients`)

Ожидается **массив объектов**; отображаемые поля включают `id`, `name`, `surname`, `money`, `phone`, `tags` (массив `{name, color}`), `email`, `date`, `card`. Названия полей у нового сервера могут отличаться — в таком случае нужен адаптер.

Форма и локальный адаптер требуют для нового клиента хотя бы одно идентифицирующее поле: имя, фамилию, телефон, email или номер карты. Телефон и обе части имени одновременно не обязательны. Новый или изменённый email проверяется по формату; неизменённые значения старых записей не переписываются автоматически. Эти проверки не заменяют серверную валидацию. POST должен вернуть созданную запись с `id`, чтобы frontend мог редактировать и удалять её.

### Карты (GET `/cards`)

Ожидается **массив объектов**, у которых используются `id`, `uid`, `amount`, `created_at`, `last_used_at` и опционально объект `user` с полями `id`, `firstname`, `lastname`.

Поле `discount` — процент скидки от 0 до 100 включительно. При отсутствии поля интерфейс показывает 0. Существующие POST `/cards` и PUT `/cards/:id` передают `discount` числом; локальный адаптер сохраняет его. Go API должен сохранять и возвращать это поле; фактическая интеграция ещё не проверена. Здесь не добавляются отдельные маршруты применения скидок или взаимодействия с оборудованием.

### Администраторы (GET `/admins`)

Ожидается **массив объектов** с полями `id`, `firstname`, `lastname`, `email`, `phone`, `role`, `special_card_uid`. Создание/обновление отправляет также `role_id` и `is_active`.

## WebSocket

Клиенты подписываются на `VITE_WS_URL` (или URL, производный от API), ожидая JSON-сообщения с `type` и `data`.

Типы событий, используемые сейчас:

- `client.created`
- `client.updated`
- `client.balance_changed`
- `client.deleted`

Пример:

```json
{ "type": "client.updated", "data": { "id": 1, "name": "Example" } }
```

`data` может быть объектом или JSON-строкой. Сначала согласуйте контракт с разработчиком Go, затем тестируйте действия и авторизацию.

## Проверка перед передачей в production

1. Единый HTTP API-клиент, в том числе для клиентов и администраторов.
2. Реальные маршруты и структуры ответов нового сервера.
3. Роли/права и корректная обработка 401/403.
4. Хранение токена, защита от XSS, CORS и HTTPS.
5. WebSocket lifecycle, reconnect и обработка сетевых ошибок.
6. Действия кнопок на экранах, сейчас работающих лишь на локальных данных.
